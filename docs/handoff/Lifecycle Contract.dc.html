One lifecycle, one look
A service layer and a visual contract for the four item kinds — flags, actions, queries and key dates — so the same operation is written once, recorded once, and rendered the same way on every surface.

2 · Five moves, against the dev plan
1 · Canonical vocabulary + CHECK constraints
→ fold into Step 3
One settled word per table: actions settle as closed, nothing else. Fix the one 'completed' writer (1446) and the 'complete' filter (7236), then add a DB CHECK constraint per status column so a wrong spelling fails loudly instead of arming quietly. Data migration cost today: zero rows.
DEV_PLAN fit: Step 3 is already the housekeeping batch of carried one-liners (won→LTA, dead columns, flag severity). This belongs beside them — same size, same PR.
2 · One service layer — the highest-leverage fix
new Step 2.5 · before Step 4
One module, one exported verb per transition: completeAction · reopenAction · acknowledgeFlag · convertFlag · resolveQuery · answerQuery · escalateQuery · markDateMet · moveDate. Each verb owns its write shape, writes its item_events entries, and rides sb so the RX bus auto-emits. Every surface — modal, meeting pane, My Work, Register, project tab, checklist routing — calls the same function.
DEV_PLAN fit: this is RX-B's rowPayload() doctrine ("so the two write paths can't drift") applied app-wide. It must land before Step 4's Register rework and Steps 8–9's new modules, which would otherwise multiply the copy count.
3 · One openness predicate, dumb loaders
same batch as move 2
Loaders fetch a scope (this project, my department), never a lifecycle slice — the .neq('acknowledged') family goes. One shared isOpen(kind, item) derives open vs settled everywhere; doneFlags / doneActions collapse into selectors over the one dataset. Fetch cost is a non-issue: the plan's own count is ~460 rows across every aggregate.
DEV_PLAN fit: generalises the Fitzrovia fix (Step 2 follow-up 2) so it can't recur per-view.
4 · One audit spine
→ Step 4 · scope with Tom first
item_events is the record; audit_log / record_activity narrows to notification fan-out (or the feed becomes a view over item_events). Interim rule, enforced by move 2: every verb emits both, so nothing diverges by path while the decision is pending.
DEV_PLAN fit: the plan explicitly defers the Register/activity-log rework to a scoping conversation — respect that; this move is its prerequisite, not its replacement.
5 · Provenance as a followable object
→ feeds Step 5 directly
The links already exist in the schema (resulting_action_id · parent_type/parent_id · cause_flag_id/cause_action_id · meeting_id) — what's missing is one threadOf(item) resolver in the service layer that walks flag → action → query → date change, plus one provenance strip rendered on every card and modal (spec below). This chain is what makes the delay record worth money; today it is reconstructed ad hoc per surface. Built once, the Step 5 chronology export is a print of the same object.
3 · The lifecycle contract
Every kind is either OPEN or SETTLED — one shared axis — with kind-specific settled states. Overdue and in-query are overlays derived at render, never stored statuses. One STATE_META map drives chip, ribbon and filter alike, so they cannot disagree.
Flag meeting_handoffs
Open → ✓ Acknowledged or → Converted converted always writes resulting_action_id; nothing reads that field as a shadow status any more
Action actions
Open ⇄ ✓ Closed the only settled word — 'completed' and 'complete' are retired and rejected by the CHECK constraint. Overlays: overdue (due < today), in query (open query attached)
Query queries
Open → ✓ Resolved escalation stays an overlay (escalated_to); ball-in-court stays derived from the thread, never cached
Key date project_key_dates
Open → ✓ Met keeps the boolean in the DB (cheap), but only markDateMet() touches it, and the UI speaks the shared vocabulary. A move is an event in programme_revisions, never a state. Overlay: slipped +Nd against baseline
